# 0001：MealOps 开发策略

- 状态：已接受
- 决策日期：2026-08-03
- 适用阶段：V1 及其准备阶段

## 背景

MealOps 同时涉及食材标准化、单位换算、菜谱、库存批次、库存流水、多餐规划、购物清单和计划执行。如果在空仓库中直接生成完整应用，模块之间很容易出现术语、数据模型、状态和事务边界不一致。

因此，在编写业务代码前先固定产品边界、事实来源、开发顺序和暂不引入的技术。本决策记录六项相互配合的开发策略。

## 决策 1：先做确定性业务系统，再接入大模型

### 选择

V1 先实现可测试、可复现、可解释的确定性业务系统。大模型聊天、Agent Tool Calling、RAG 和向量数据库不进入 V1。未来的大模型只能通过受控应用服务或工具使用业务能力，不能直接修改数据库。

### 优势

- 库存、计划和购物清单拥有唯一且可审计的事实来源；
- 规划规则可用固定输入验证，问题可以稳定复现；
- 过敏、忌口、库存扣减等关键约束不依赖模型概率输出；
- 后续可以独立评估自然语言理解、工具选择和业务算法。

### 代价

- 前期需要明确领域模型和规划规则；
- 在没有自然语言入口时，用户需要使用结构化表单；
- 确定性规划器需要显式处理约束、权重和搜索空间。

### 未选择的替代方案

- 让大模型直接生成餐食计划：开发演示快，但结果不可复现，难以保证库存核算和硬约束。
- 让大模型直接读写数据库：减少接口层工作，但破坏权限、事务、幂等和审计边界。
- 从 RAG 菜谱问答开始：能展示 AI，但不能验证库存到购物清单的核心闭环。

### 调整条件

当核心业务 API、规划器和状态机稳定，且具备工具调用评测、写操作确认、权限与审计机制后，可以增加自然语言和 Agent 层。模型仍不取代确定性事实来源。

## 决策 2：选择模块化单体，而不是微服务

### 选择

V1 使用模块化单体，按食材、菜谱、库存、偏好、计划、规划器和购物清单等业务域划分边界，在一个可部署应用中协作。

### 优势

- 跨库存、流水、计划和购物清单的事务更清晰；
- 本地开发、测试、部署和故障定位成本较低；
- 仍能通过模块依赖和接口表达领域边界；
- 更适合个人项目当前的规模和迭代速度。

### 代价

- 所有模块共享一个部署节奏；
- 若边界约束执行不严，可能退化为耦合的单体；
- 无法独立扩缩某个模块。

### 未选择的替代方案

- 微服务：可以独立部署和扩缩，但会提前引入服务发现、网络失败、分布式事务、可观测性和运维成本。
- 无模块分层的传统单体：初始化简单，但业务规则容易散落，后期难以测试和演进。
- Serverless 函数集合：适合独立事件任务，但当前核心闭环包含较强事务和状态协作。

### 调整条件

只有当出现明确的独立扩缩需求、团队所有权边界、部署节奏冲突或单体无法满足的隔离要求，并且已有稳定模块接口与可观测性后，才评估拆分服务。不能仅为展示技术而拆分。

## 决策 3：先实现 H5，再适配微信小程序

### 选择

V1 先交付移动端优先的 H5 页面，核心闭环稳定后再评估微信小程序适配。

### 优势

- 可直接使用浏览器调试、自动化测试和演示；
- 不依赖微信登录、开发者资质、审核和订阅消息；
- 能优先验证产品流程和后端契约；
- 降低早期平台专属能力对产品设计的干扰。

### 代价

- 首版缺少微信生态入口和原生能力；
- 后续适配小程序时仍需处理平台限制和交互差异；
- 某些设备能力在 H5 上体验有限。

### 未选择的替代方案

- 直接开发微信原生小程序：平台体验更直接，但会把登录、审核、开发工具和平台 API 提前带入 V1。
- 同时开发 H5 与小程序：覆盖面更广，但显著增加首版测试矩阵和兼容成本。
- 先开发桌面 Web：开发方便，但不符合用户在厨房和购物场景中的移动端使用习惯。

### 调整条件

当 H5 核心流程、API 和状态处理稳定，且明确需要微信分发、登录或订阅提醒时，再进入小程序适配节点。具体前端框架为“待确认”，应在工程选型节点决定。

## 决策 4：V1 不使用 Redis 和消息队列

### 选择

V1 使用数据库和应用内同步流程完成核心闭环，不引入 Redis 或消息队列。

### 优势

- 减少部署组件、数据一致性路径和故障模式；
- 先通过真实查询和性能数据识别缓存需求；
- 库存与计划写操作可以在明确的数据库事务中完成；
- 避免在业务规则尚未稳定时处理缓存失效、重复消费和消息顺序。

### 代价

- 高并发读场景没有专用缓存；
- 临期提醒等异步能力需要后续补充；
- 长耗时任务暂时不能依靠队列解耦。

### 未选择的替代方案

- 预先使用 Redis 缓存菜谱和候选：可能降低查询延迟，但在查询模式和热点未知时会引入无依据的缓存与失效逻辑。
- 预先使用消息队列处理库存事件：能解耦消费者，但增加最终一致性、幂等消费和运维成本。
- 使用 Redis 分布式锁保护库存：当前模块化单体更适合数据库事务和乐观锁，分布式锁会增加续期与锁状态问题。

### 调整条件

当压测或生产指标证明数据库读压力和延迟无法满足目标时，才引入针对明确查询的缓存；当出现可靠异步通知、跨系统事件或需要削峰的任务，并已设计 Outbox、幂等消费和重试策略时，才引入消息队列。性能目标为“待确认”。

## 决策 5：按纵向业务闭环开发，不一次创建所有数据库表

### 选择

每个节点交付从领域规则到持久化、接口、测试和文档的最小完整纵向切片。数据库表随已确认的业务节点通过 Flyway 迁移增加，不先一次性建立全量模型。

### 优势

- 每个节点可以独立运行、测试、审查和提交；
- 表结构来自已验证用例，减少猜测性字段和关系；
- 领域术语、约束、接口和测试能同步演进；
- 发现模型问题时，影响范围更小且变更历史清楚。

### 代价

- 需要维护迁移演进，初期迁移文件数量会增加；
- 跨域的完整视图不会在第一天出现；
- 某些后续需求可能要求新增字段或重构关系。

### 未选择的替代方案

- 先建立所有数据库表：看起来完整，但容易固化未经验证的假设，并诱导生成空壳 CRUD。
- 先做所有后端层再统一补测试：短期文件多，但无法按业务结果验收，错误会积累到集成阶段。
- 仅做前端原型再反推模型：有助于交互验证，但不能替代库存事务、单位换算和规划约束的领域验证。

### 调整条件

如果多个即将实现的纵向节点共享不可分割的数据库不变量，可以在同一经批准节点中联合设计，但仍必须说明共同验收边界，不能借机创建无用的未来表。

## 决策 6：第 0 节点只建立仓库边界与规则

### 选择

第 0 节点只创建 Git 仓库、项目协作规则、产品愿景、MVP 范围、核心用户流程和本决策记录。不创建后端、前端、数据库、容器、依赖或业务代码。

### 优势

- 后续任务拥有稳定的术语、范围和完成标准；
- 可以通过 Git 审查每个节点的实际变更；
- 避免工程骨架反向决定尚未确认的产品模型；
- 第一份提交具有单一、可解释的目的。

### 代价

- 当前提交没有可运行应用；
- 技术选型、架构细节和测试命令仍需后续节点确认；
- 文档需要在后续决策变化时持续维护。

### 未选择的替代方案

- 在初始化时同时生成全栈工程：可以更快看到页面，但会混合产品、架构和实现决策。
- 只依赖任务提示词而不维护仓库规则：减少文件数量，但多线程任务容易遗漏或产生不一致规则。

### 调整条件

本节点完成并经人工审查后，才能进入下一节点。下一节点的具体目标与技术选择必须由用户明确确认，不由 Codex 自动推断。

## 结果

上述策略共同形成以下顺序：

产品边界与规则 → 确定性后端 → 规划器 → H5 前端 → Agent → 工程增强。

尚未确认的技术框架、数据库细节、身份方案、规划器参数、预算价格来源和性能目标，必须在对应节点中显式决策。
