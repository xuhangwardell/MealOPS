# MealOps V1 MVP 范围

## 1. 范围目标

V1 要验证一个最小但完整的业务闭环：用户维护菜谱、偏好和库存后，系统能针对未来 1～3 天生成多个可解释的餐食计划候选，正确核算食材缺口并形成购物清单；用户执行计划后，系统能根据确认结果更新计划和库存状态。

V1 不以覆盖所有家庭饮食场景为目标，也不以堆叠 AI 或分布式基础设施为目标。

## 2. V1 包含

### 2.1 标准食材及别名

- 维护标准食材；
- 为同一标准食材维护多个别名；
- 通过标准名称或别名解析同一食材身份。

### 2.2 单位及同维度单位换算

- 支持质量、体积、数量等单位维度；
- 支持同维度的确定性换算；
- 不允许在没有食材级规则时跨维度强行换算。

数量单位中“个、枚、包、盒”的可换算边界为“待确认”。

### 2.3 结构化菜谱

- 保存名称、基础份数、烹饪时间、适用餐次、带饭与隔夜属性等结构化信息；
- 菜谱食材引用标准食材、数量和单位；
- 保存有序制作步骤；
- 支持按目标份数缩放确定性用量。

### 2.4 库存批次和库存流水

- 同一种食材可以存在多个库存批次；
- 批次记录数量、购入时间、开封状态、保质期和状态；
- 消耗时优先使用已开封、较早到期、较早入库的批次；
- 任何入库、消耗、调整、丢弃或过期变化都保留库存流水。

库存精度等级是否在 V1 同时支持精确、近似和仅可用三种模式为“待确认”。

### 2.5 用户饮食偏好

- 保存过敏与忌口等硬约束；
- 保存喜欢、不喜欢、可用厨具和可接受难度等偏好信息；
- 规划器能区分不可违反的硬约束与可权衡的软偏好。

### 2.6 未来 1～3 天的用餐时间槽

- 用户选择日期和餐次；
- 每个时间槽保存人数、最大烹饪时间和是否需要带饭等约束；
- 不要求按固定周历一次规划整周。

### 2.7 确定性餐食规划器

- 从结构化菜谱中召回候选；
- 执行硬约束过滤；
- 根据库存覆盖、临期利用、偏好、时间和难度等特征评分；
- 组合多个餐次并考虑食材复用、重复惩罚和做饭次数；
- 返回多个候选及分项解释；
- 固定输入和规则得到稳定、可测试的结果。

候选规模、评分权重、搜索算法参数和 Leftover 的首期细则为“待确认”。

### 2.8 食材需求聚合

- 按菜谱份数计算每顿需求；
- 将可换算数量归一到统一单位；
- 按标准食材聚合整个计划的需求；
- 对不可兼容单位返回可解释结果。

### 2.9 现有库存抵扣

- 只使用有效库存参与抵扣；
- 按既定批次顺序模拟分配；
- 生成计划或购物清单时不提前实际扣减库存；
- 输出需求量、可用量和缺失量。

### 2.10 购物清单生成

- 根据聚合需求与库存差额生成草稿；
- 购物项引用标准食材和缺失数量；
- 计划发生替换或跳过时重新计算相关差额。

预算与购物清单金额所依赖的价格来源为“待确认”；在来源确定前不得假设已接入真实商品价格。

### 2.11 餐食计划状态操作

- 用户可以确认候选计划；
- 用户可以完成、跳过或替换某个餐食；
- 完成时由用户确认实际使用量后更新库存；
- 跳过时不自动扣减库存；
- 替换后重新校验约束并计算购物清单。

### 2.12 移动端优先的 H5 页面

- 提供库存、菜谱、规划、候选解释、购物清单和个人偏好的最小交互页面；
- 优先在浏览器完成端到端调试和演示；
- 页面必须处理加载、空数据、错误和重试状态。

具体前端框架在工程选型节点确认，本节点不创建前端工程。

## 3. V1 明确不包含

1. 微信登录；
2. 微信订阅消息；
3. 外卖平台接入；
4. 超市真实下单；
5. 支付；
6. 营养或医疗建议；
7. 图片识别；
8. 小票 OCR；
9. 大模型聊天；
10. Agent Tool Calling；
11. 多人家庭协作；
12. 微服务；
13. Redis；
14. 消息队列。

以下能力同样不应借其他名称提前进入 V1：RAG、向量数据库、真实零售 SKU 匹配、微信专属能力和由 LLM 直接生成最终计划。

## 4. MVP 验收场景

给定库存：鸡胸肉临期、西兰花三天后到期，并有鸡蛋、番茄和米；用户要求在未来两天安排四顿饭，其中一顿需要带饭、每次烹饪不超过 30 分钟，并优先减少浪费和做饭次数。

系统应能够：

1. 过滤违反硬约束的菜谱；
2. 返回多个排序稳定的计划候选；
3. 优先利用鸡胸肉和西兰花等临期库存；
4. 明确展示跨餐复用或一次制作多份带来的影响；
5. 聚合四顿饭的食材需求；
6. 使用有效库存抵扣；
7. 生成缺失食材购物清单；
8. 展示预计做饭次数和选择理由；
9. 在用户完成、跳过或替换餐食后保持计划、购物清单与库存一致。

验收数据的精确数量、候选菜谱和期望分数为“待确认”，将在相应纵向节点建立固定测试数据集。

## 5. 范围变更规则

任何新增能力必须先回答：

1. 是否是完成当前 MVP 闭环的必要条件；
2. 是否能够在当前节点独立验收；
3. 是否引入尚未批准的基础设施或外部依赖；
4. 是否会改变已确定的事实来源或状态边界。

若答案涉及范围扩大，必须先更新本文档和相应决策记录，不得直接实现。
